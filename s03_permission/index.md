# s03 · Permission — 先划边界，再给自由

> *"模型要自由，harness 给边界。"*

## 本章要解决的问题

s02 的 agent 已经能读写文件、跑命令了——但它是**不设防**的。模型一个幻觉就可能 `rm -rf /`，或者悄悄改动你不该碰的文件。

一个能交付的 agent 产品必须有**权限闸门**：在工具真正执行之前，先问一句"这个操作能不能做？要不要问用户？"

## 核心设计：规则三态

每一条权限规则把一类操作归到三种决定之一：

```
                 tool_use 到达
                      |
          +-----------+-----------+
          |                       |
       命中规则              未命中任何规则
          |                       |
   +------+------+          走默认策略
   |      |      |          (本例=ask)
 allow    ask   deny
   |      |      |
 放行   问用户   直接拒绝
        y/n/a
```

- **`allow`** — 只读、无副作用的操作（`ls`、`read_file`）直接放行，不打扰用户。
- **`ask`** — 破坏性或不可逆的操作（`rm`、`git push`、写 `.env`）弹出确认。
- **`deny`** — 绝对禁止的操作（`rm -rf /`、`sudo`），不给任何商量余地。

```python
PERMISSION_RULES = [
    ("bash", r"rm\s+-rf\s+/",   "deny"),    # 永远禁止
    ("bash", r"\brm\b",         "ask"),     # 删除要确认
    ("bash", r"^(ls|cat|grep)", "allow"),   # 只读直接放行
    ("write_file", r"\.env",    "ask"),     # 碰密钥文件要确认
]
```

**规则按顺序匹配，第一条命中生效**——所以要把更严格的 `deny` 写在前面。

## 两个工程细节

### 1. 会话内记忆（session grants）

用户如果反复被同一个操作打断，会很烦。所以闸门支持 `[a]本次会话总是允许`：批准后把 `(工具, 参数)` 记进 `session_grants`，同样的调用不再问。注意它**只在本次会话有效**，不写盘——安全边界不该轻易持久化。

### 2. 拒绝也要给模型出路

被拒绝时不能只是沉默报错，要返回一句**模型能理解、能据此改道**的话：

```python
return "权限拒绝: 该操作被安全策略禁止，请换用其他方式。"
```

模型读到这句，通常会自己退而求其次（比如改用更安全的方式，或直接向用户说明）。这是把"权限"接进 agent loop 的正确姿势——**拒绝本身也是一种工具结果**。

## 试一试

> **安全提示**：代码会执行模型生成的 shell 命令。建议在一个临时测试目录中运行。

```sh
python s03_permission/code.py
```

试试这些 prompt：

1. `创建一个 temp 目录，然后删掉它`
2. `执行 sudo ls 看看有什么`
3. `把 .env 文件里的 MODEL_ID 改成 gpt-5`

**观察重点**：每次工具调用前都先过一遍 `PermissionGate`——allow / ask / deny 三态，规则按顺序匹配。

- Prompt 1：模型会先 `mkdir`（命中 allow 规则直接放行），再 `rm`（触发 ask，弹出紫色的 `⚠ 需要确认`）。试试输入 `a`——本次会话里相同调用不再重复询问（`session_grants`）。
- Prompt 2：`sudo` 命中 deny 规则，不弹询问框、直接拒绝。注意模型不会硬来，而是告诉你它做不了——被拒绝的操作以 tool_result 回传，模型读到后自己改道。
- Prompt 3：`write_file` 碰到 `.env` 也要确认——权限系统管的不只是 bash，任何工具都能挂规则。
